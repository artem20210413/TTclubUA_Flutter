# Дослідження Фази 0: Екран мапи з учасниками по містах

## 1. Мап-рушій для кожної платформи

**Рішення**: iOS використовує `apple_maps_flutter` (обгортка над нативним `MKMapView`/Apple Maps). Android використовує `flutter_map` з растровими тайлами OpenStreetMap (`latlong2` для координат).

**Обґрунтування**: Специфікація явно вимагає нативні Apple Maps на iOS. Для Android природним аналогом є `google_maps_flutter`, але він потребує проєкту в Google Cloud, API-ключа та білінг-акаунту (навіть "безкоштовний рівень" вимагає увімкненого білінгу) — користувач підтвердив, що це небажане ускладнення. `flutter_map` + тайли OSM не потребують API-ключа, білінгу чи ліміту використання для розумного трафіку застосунку, і є добре підтримуваним, широко використовуваним Flutter-пакетом.

**Розглянуті альтернативи**:
- `google_maps_flutter` на Android — відхилено: вимагає API-ключ з увімкненим білінгом, суперечить вимозі "безкоштовне".
- Єдиний кросплатформний рушій (`flutter_map` і на iOS, і на Android) — відхилено: специфікація явно вимагає *нативні* Apple Maps на iOS, а не рендеринг тайлів OSM.
- `mapbox_gl` — відхилено: також потребує API-токен і має біллінг понад безкоштовну квоту.

## 2. Стратегія рендерингу міток

**Рішення**: Єдиний спільний Flutter-віджет, `CityMapMarker`, рендерить вигляд кола-аватарки або бейджа-лічильника (побудований на `TTNeumorphicBox`/`CircleAvatar`). Кожна платформна реалізація екрана відповідає за перетворення цього віджета на мітку/анотацію через API свого рушія:
- `apple_maps_flutter`: позиції `Annotation` підтримують кастомну іконку; оскільки мітки `apple_maps_flutter` базуються на зображеннях (не довільних віджетах), спільний віджет `CityMapMarker` растеризується у зображення (через `RepaintBoundary` + `toImage`) один раз для кожної унікальної комбінації даних міста (аватарка+кількість) і кешується, після чого передається як іконка анотації.
- `flutter_map`: мітки — це нативні Flutter-віджети через `MarkerLayer`, тому `CityMapMarker` використовується напряму як дочірній елемент мітки без растеризації.

**Обґрунтування**: Тримає всю візуальну логіку (стилізацію, ефект TTNeumorphicBox, запасний варіант аватарки, форматування лічильника) в одному місці, задовольняючи вимогу "мають виглядати однаково" без дублювання дизайн-логіки для двох платформ. Різниться лише "клейовий" код "як передати цей віджет саме в цей мап-рушій".

**Розглянуті альтернативи**: Повністю окремі віджети міток для кожної платформи — відхилено, подвоює обсяг роботи для суто візуальної задачі та ризикує візуальним розходженням між iOS/Android з часом.

## 3. Дозвіл на геолокацію та позиціонування

**Рішення**: Використати пакет `geolocator`: викликати `Geolocator.checkPermission()`/`requestPermission()` один раз при вході на екран (в `initState`), потім `Geolocator.getCurrentPosition()`. У разі успіху центрувати камеру на цій позиції, зум 6.0. У разі будь-якої відмови/помилки (`PermissionDeniedException`, `LocationServiceDisabledException`, таймаут тощо) — відкат до Києва (50.4501, 30.5234), зум 6.0 — обробляти всі режими помилок однаково згідно з крайніми випадками специфікації, без окремої обробки для кожного типу помилки.

**Обґрунтування**: `geolocator` є де-факто стандартним Flutter-пакетом для геолокації (прямо згаданий в описі функції) і вже обробляє налаштування дозволів для iOS/Android (все ще потрібно додати `NSLocationWhenInUseUsageDescription` в `Info.plist` та дозвіл `ACCESS_FINE_LOCATION` в `AndroidManifest.xml`).

**Розглянуті альтернативи**: Написання platform channels вручну — відхилено, повторне винайдення вже вирішеної проблеми.

## 4. Кешування зображень для аватарок

**Рішення**: Використати `cached_network_image` як для аватарок міток, так і для аватарок рядків у шторці, з дефолтним диск+пам'ять cache manager.

**Обґрунтування**: Прямо задовольняє FR-009 (без повторного завантаження в межах сесії) та SC-005, без жодного кастомного коду кешування. У кодовій базі немає наявного рішення для кешування (підтверджено дослідженням), тож це нове, низькоризикове додавання; коректно деградує до `errorBuilder` для запасного варіанту (використовується для запуску відображення "стандартний кружок з 1" / ініціали з FR-007/FR-014).

**Розглянуті альтернативи**: Ручний `Image.network` + саморобний `Map<String, Uint8List>` кеш — відхилено як зайве повторне винайдення.

## 5. Патерн доступу до API

**Рішення**: Додати дві нові функції до наявного файлу `lib/api/routs/cities/CityServices.dart` (розширюючи наявний домен-специфічний файл, а не вводячи нову абстракцію "ApiClient"), використовуючи `package:http` (домінантний патерн у кодовій базі; `dio` використовується лише у 2 файлах і не є конвенцією для розширення):
- `fetchCityMapPoints()` → `GET api/cities/map`
- `fetchCityMembers(int cityId, {int page})` → `GET api/cities/{id}/users`

Обидві дотримуються наявного патерну функцій у стилі `SEARCH_USER` (`lib/api/routs/user.dart`), читаючи константи базового URL з `lib/api/routs/root.dart` та заголовки автентифікації через наявний хелпер `HEADERS(token)`.

**Обґрунтування**: Точно відповідає конвенції проєкту (підтверджено: центрального API-клієнта немає; `http` домінує; DTO пишуться вручну, а не генеруються).

**Розглянуті альтернативи**: Впровадження Dio + interceptors як нового стандарту — відхилено, поза обсягом цієї функції та несумісно з 95% наявних викликів.

## 6. Форма DTO

**Рішення**: Два нові ручні DTO, що відображають стиль наявних `CityDto`/`UserSmallDto` (фабрика `fromJson` з дефолтами через `??` та `(json['x'] as num?)?.toDouble()` для double; зберігати сирий JSON `Map`, лише якщо екрану знадобляться прохідні поля, за зразком `UserSmallDto`):
- `CityMapPointDto`: `id`, `name`, `latitude`, `longitude`, `usersCount`, `avatarUrl` (nullable)
- `CityMemberDto`: `id`, `name`, `profileImage`, `roles` (List<String> або схожа наявна форма ролей — уточнити за `UserSmallDto`/`UserUpdateDto` під час реалізації), `telegramNickname` (nullable), `instagramNickname` (nullable), `updatedAt`

**Обґрунтування**: Узгодженість з усіма іншими DTO в `lib/api/routs/Dto/`; у проєкті ніде не використовується `json_serializable`/build_runner, тож впровадження його тут було б невиправданою новою залежністю.

## 7. Патерн пагінації для списку учасників у шторці

**Рішення**: Повторно використати патерн `SearchUser.dart`: `_page` int починається з 1, `_hasMore` bool, слухач `ScrollController`, що спрацьовує біля `maxScrollExtent`, евристика `_hasMore = data.length >= pageSize` (розмір сторінки має відповідати дефолту `GET api/cities/{id}/users`, підтвердити під час реалізації за живим контрактом бекенду).

**Обґрунтування**: Точно відповідає наявній робочій реалізації нескінченної прокрутки в застосунку; нової абстракції пагінації не потрібно.

## 8. Патерн UI для шторки

**Рішення**: Повторно використати патерн `showModalBottomSheet<T>(isScrollControlled: true, backgroundColor: TTColors.background, ...)` з `CitiesPicker.dart`, з `StatefulBuilder`/окремим `StatefulWidget` (`CityMembersBottomSheet`), що володіє власним станом пагінації, заголовком (назва міста + кількість) та списком рядків, побудованих на `TTNeumorphicBox`.

**Обґрунтування**: Відповідає єдиному наявному прикладу bottom sheet у кодовій базі; зберігає узгодженість візуальної мови (неоморфне оформлення) з рештою застосунку.

## 9. Перехід до профілю учасника

**Рішення**: Кожен рядок у шторці переходить через `Navigator.push(context, MaterialPageRoute(builder: (_) => Profile(id: member.id)))`, відповідно до фактичного конструктора `Profile` (`Profile({super.key, this.id})`, nullable `int? id`) та наявної конвенції навігації в застосунку (без named routes/go_router у цьому проєкті).

**Обґрунтування**: Прямо підтверджено за конструктором `Profile.dart`; нова навігаційна інфраструктура не потрібна.
