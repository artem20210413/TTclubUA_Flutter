# Модель даних Фази 1: Екран мапи з учасниками по містах

Два нові DTO, за наявною конвенцією ручних `fromJson`/`toJson` (див. `lib/api/routs/Dto/City/CityDto.dart`, `lib/api/routs/Dto/User/UserSmallDto.dart`). Локального збереження немає — обидва є тимчасовими моделями відповіді в пам'яті.

## CityMapPointDto

Представляє одну мітку на мапі (елемент списку `GET api/cities/map`). Відповідає сутності специфікації **Точка мапи міста**.

| Поле | Тип | Nullable | Примітки |
|---|---|---|---|
| `id` | `int` | ні | Ідентифікатор міста; використовується для запиту списку учасників при тапі |
| `name` | `String` | ні | Назва міста, показується у заголовку шторки |
| `latitude` | `double` | ні | Парситься через `(json['latitude'] as num?)?.toDouble() ?? 0` |
| `longitude` | `double` | ні | Парситься через `(json['longitude'] as num?)?.toDouble() ?? 0` |
| `usersCount` | `int` | ні | Визначає рендеринг мітки (одна аватарка чи бейдж з числом) (FR-006–FR-008) |
| `avatarUrl` | `String?` | так | Репрезентативна аватарка; `null` примусово вмикає бейдж з числом за FR-008, навіть якщо `usersCount == 1` |

**Правила валідації/похідні**:
- Мітка рендериться лише якщо `usersCount >= 1` (міста з 0 учасниками відсутні у відповіді, або відфільтровуються на клієнті захисно, згідно крайніх випадків).
- `showsAvatar = usersCount == 1 && avatarUrl != null` (FR-006); інакше показується бейдж з числом (FR-008).

## CityMemberDto

Представляє один рядок у пагінованому списку учасників міста (елемент списку `GET api/cities/{id}/users`). Відповідає сутності специфікації **Учасник міста**.

| Поле | Тип | Nullable | Примітки |
|---|---|---|---|
| `id` | `int` | ні | Використовується для переходу на `Profile(id: ...)` |
| `name` | `String` | ні | Ім'я для відображення |
| `profileImage` | `String?` | так | Якщо `null`, дорівнює відомому дефолтному плейсхолдеру (`profile_picture.webp`), або зображення не завантажилось — показується запасна аватарка (ініціали/фірмова іконка) (FR-014) |
| `roles` | `List<String>` | ні (дефолт `[]`) | Показується як компактна другорядна інформація у рядку (FR-013); повне відображення — на екрані `Profile` |
| `telegramNickname` | `String?` | так | Опускається з рядка, якщо відсутнє |
| `instagramNickname` | `String?` | так | Опускається з рядка, якщо відсутнє |
| `updatedAt` | `DateTime?` | так | Парситься з рядка ISO 8601, якщо присутній; використовується для відображення "останнє оновлення" |

**Правила валідації/похідні**:
- `hasDefaultAvatar = profileImage == null || profileImage!.endsWith('profile_picture.webp')` → запускає відображення запасної аватарки.

## Обгортка пагінованої відповіді

Очікується, що `GET api/cities/{id}/users` повертає пагінований список (стандартна REST-пагінація — номер/розмір сторінки, або індикатор `has_more`/`next_page`). Точна форма підтверджується за живим контрактом бекенду під час реалізації; клієнтський стан пагінації (`_page`, `_hasMore`) не потребує окремого типізованого DTO для обгортки — `CityMemberDto.fromJson` застосовується поелементно до того поля списку, яке містить відповідь, за зразком наявного патерну `SearchUser.dart`, що трактує обгортку не строго типізовано.

## Зв'язки

- `CityMapPointDto.id` — ключ, що використовується для запиту сторінок `CityMemberDto` для цього міста; клієнтський join не потрібен — шторка завжди запитує свіжі дані учасників для тапнутого id міста, а не повторно використовує дані точки мапи.
- Зв'язок між `CityMemberDto` та наявними повними моделями `User`/`UserSmallDto` застосунку моделювати не потрібно, окрім спільного `id`, який передається напряму в `Profile(id: ...)`.
