# План реалізації: Екран мапи з учасниками по містах

**Гілка**: `001-city-users-map` | **Дата**: 2026-07-26 | **Специфікація**: [spec.uk.md](./spec.uk.md)

**Вхідні дані**: Специфікація функції з `/specs/001-city-users-map/spec.md`

**Примітка**: Цей шаблон заповнюється командою `/speckit-plan`; його визначення описує послідовність виконання.

## Резюме

Додати новий Flutter-екран, що показує мапу міст, де знаходяться учасники клубу. На iOS мапа рендериться через нативні Apple Maps (`apple_maps_flutter`); на Android — через `flutter_map` з тайлами OpenStreetMap (повністю безкоштовно, без API-ключа/білінгу). На обох платформах використовується однаковий кастомний Flutter-віджет мітки (аватарка в колі або бейдж із числом), який рендериться як платформо-специфічна анотація/маркер, тому візуальний результат ідентичний, хоча два мап-рушії підключають мітки по-різному "під капотом". Екран запитує дозвіл на геолокацію через `geolocator`, центрує камеру на користувачі (зум 6.0) або відкатується до Києва, завантажує дані міток міст з `GET api/cities/map` і відкриває пагіновану шторку (`GET api/cities/{id}/users`) при тапі на мітку, рядки якої ведуть на наявний екран `Profile`. Нативні кнопки зуму +/- та "моя локація" на екрані додаються окремо для кожної платформи через власне API камери відповідного рушія.

## Технічний контекст

**Мова/Версія**: Dart (SDK `^3.5.4`, за `pubspec.yaml`), стабільна версія Flutter

**Основні залежності**: `apple_maps_flutter` (нативна мапа iOS), `flutter_map` + `latlong2` (мапа Android, тайли OSM), `geolocator` (дозвіл на геолокацію + позиція), `cached_network_image` (кешування аватарок) — усі нові додавання до `pubspec.yaml`; наявний пакет `http` повторно використовується для API-запитів згідно з конвенцією проєкту (див. research.md)

**Сховище**: Н/З — немає локального збереження, окрім стану в пам'яті/кешу зображень; усі дані міст/учасників завантажуються наживо з наявного backend API

**Тестування**: `flutter_test` (наявна `dev_dependency`); ручна перевірка через `quickstart.md`, оскільки у проєкті немає наявного набору widget/integration тестів для подібних екранів

**Цільова платформа**: Екрани мобільного застосунку для iOS (нативні Apple Maps) та Android (flutter_map/OSM), додані до наявного Flutter-застосунку

**Тип проєкту**: Мобільний застосунок (єдина кодова база Flutter, платформо-умовний віджет мапи)

**Цілі продуктивності**: Екран мапи інтерактивний (мітки видимі) протягом ~2с при "теплому" запуску застосунку за нормальних умов мережі; зображення аватарок міток/списку, які вже переглядались протягом сесії, не повинні завантажуватись повторно (сприймається як миттєве повторне відображення)

**Обмеження**: Обов'язково повторно використати `TTScaffold` та `TTNeumorphicBox` для оформлення екрана/мітки/рядків списку; дотримуватись наявної конвенції ручних DTO (`XxxDto.fromJson`/`toJson`) у `lib/api/routs/Dto/City/`; не вводити нову абстракцію API-клієнта — дотримуватись наявного стилю функцій по доменах у `lib/api/routs/<domain>/`; мап-рушій для Android має бути безкоштовним/без API-ключа (з цієї причини відхилено `google_maps_flutter`)

**Масштаб/Обсяг**: 1 новий екран, 2 нові DTO (точка мапи міста, учасник міста), 1 новий компонент шторки, 2 нові функції API-запитів, платформо-умовний рендеринг міток для 2 мап-рушіїв

### Вихідний код (корінь репозиторію)

Це єдина кодова база Flutter-застосунку (не поділ на web/backend); функція додає файли у наявне дерево `lib/`, дотримуючись поточних конвенцій (пласкі `pages/`, домен-специфічні `api/routs/<domain>/`, спільні `components/`).

```text
lib/
├── api/
│   └── routs/
│       ├── Dto/
│       │   └── City/
│       │       ├── CityDto.dart              # наявний
│       │       ├── CityMapPointDto.dart       # НОВИЙ - елемент GET api/cities/map
│       │       └── CityMemberDto.dart         # НОВИЙ - елемент GET api/cities/{id}/users
│       └── cities/
│           └── CityServices.dart              # наявний файл; ДОДАТИ fetchCityMapPoints(), fetchCityMembers(cityId, page)
├── components/
│   ├── TTScaffold.dart                        # наявний, використовується без змін
│   ├── TTNeumorphicBox.dart                    # наявний, використовується для бейджа мітки / шторки
│   └── map/
│       ├── CityMapMarker.dart                  # НОВИЙ - спільний віджет мітки з аватаркою/лічильником (для обох платформ)
│       └── CityMembersBottomSheet.dart         # НОВИЙ - пагінована шторка списку учасників
└── pages/
    └── Nav/
        └── Map/
            ├── CityUsersMapScreen.dart         # НОВИЙ - точка входу екрана, використовує TTScaffold
            ├── CityUsersMapScreen.ios.dart      # НОВИЙ - реалізація apple_maps_flutter (умовний імпорт)
            └── CityUsersMapScreen.android.dart  # НОВИЙ - реалізація flutter_map/OSM (умовний імпорт)

test/
└── (лише ручна перевірка для цієї функції — див. quickstart.md; немає наявного
    widget/integration тест-набору для подібних екранів, який можна розширити)
```

**Рішення щодо структури**: Єдиний Flutter-проєкт (наявне дерево `lib/`). Платформо-специфічні мап-рушії ізольовані за однією точкою входу екрана (`CityUsersMapScreen.dart`), яка умовно збирає реалізацію для iOS чи Android (через `dart:io Platform.isIOS`/`isAndroid`, узгоджено з тим, як решта застосунку вже розгалужується для платформо-специфічної поведінки), тому решта застосунку (навігація, DTO, шторка, екран Profile) платформо-незалежна та спільна.

## Відстеження складності

> Гейтів конституції ще не визначено (шаблон незаповнений), тож обґрунтовувати порушення не потрібно. Єдиний свідомий компроміс складності — два мап-рушії замість одного — випливає безпосередньо з явної вимоги (нативні Apple Maps на iOS, безкоштовний рушій на Android) і повністю міститься у двох файлах `CityUsersMapScreen.*.dart`; усе інше у функції (DTO, API-виклики, шторка, контракт віджета мітки) спільне.
